Chapter 1 · Machines

1 · Which machines are truly underperforming?

Luck and location explain the list. None of the GM's 10 draws weak play, and all ten are profitable after costs.

How we measured this

A machine's luck score (z) is (actual house win − theo) ÷ the standard deviation expected from luck alone. That standard deviation is computed exactly from each machine's sum_bet_squared × its game's payout_multiplier_variance. A score between −2 and +2 is ordinary luck. Demand is measured as theo per day on the floor: what the machine should earn given how much it was played, which removes luck.

How each reason is assigned: Hit-rate mismatch hit-rate z beyond ±5 (see the Leak Detector). Payout anomaly luck score ≤ −3 (≈1-in-740 by luck; with 300 machines we'd expect ~0.4 by chance). Watch score ≤ −2. Short tenure under 90 days on the floor. Location zone's median theo/day below 80% of the floor median. Low-edge game configured RTP ≥ 95%, so low theo by design. Weak play coin-in/day below 75% of its zone's median, the only sign that the machine itself is unattractive. Normal otherwise. Source: machine_day ⋈ game_math ⋈ floor_locations.

Leak Detector

Leak Detector: two independent tests

One machine fails both tests: M-1158 pays on 38.6% of spins vs 31.5% configured, in two independent systems.

How we measured this

A luck score alone can't separate bad luck from a broken machine. So we add a second test that luck barely touches: hit frequency. Each game's hit_probability says what share of spins should pay something. Over ~700,000 spins, the real share should land within a fraction of a point of it. Hit-rate z = (hits − p·spins) ÷ √(p(1−p)·spins). A machine that fails both tests is very likely misconfigured, not unlucky. This audit uses only standard meter data, so any operator or regulator could run it monthly at no cost.

Payout luck vs hit frequency (click a dot to open it in the Luck Lens)

Luck Lens:

The Luck Lens plots cumulative (house win − theo). The shaded band is ±2σ of pure luck, which widens as play accumulates. A healthy machine wanders inside it; a leak drifts out and stays out. Competing explanation, tampering: the 80 reported tampering attempts are scattered (at most 3 on any machine), and none involve M-1158. A steady 38.6% hit rate from January 1 fits a configuration or records mismatch, not an intermittent intrusion. Code: analysis/hit_audit.py.

Powered by Tiger Data

The leak alarm, live: caught on day one

Running the same hit-rate test every hour in Tiger Data, M-1158 trips the alarm after 10 hours of play, with zero false alarms on the other 309 machines.

How we measured this

All 1,321,908 hourly meter rows are loaded into a TimescaleDB hypertable on Tiger Cloud (7-day chunks, columnstore segmented by machine), next to relational tables for machines, game settings and floor locations. A continuous aggregate rolls them up by gaming day (06:00 Las Vegas time, real-time aggregation on, refreshed every 15 minutes), and the leak_monitor view computes each machine's hit-rate z from it. The early-warning query applies the alarm rule |z| ≥ 5 to every machine's cumulative hits and spins, hour by hour. Benchmarks are server-side execution times (median of 5, EXPLAIN ANALYZE), so network latency is excluded. Tiger totals match the local analysis exactly.

First week, hour by hour: cumulative hit-rate z

Same questions, three storage layouts: server time (ms, log scale)

The SQL a floor team would run (live monitor)
CREATE MATERIALIZED VIEW meter_daily WITH (timescaledb.continuous, timescaledb.materialized_only = false) AS
SELECT time_bucket('1 day', ts, 'America/Los_Angeles', "offset" => interval '6 hours') AS day,
       machine_id, location_id, sum(spins) spins, sum(hits) hits, sum(coin_in_cents) coin_in_cents
FROM meter_hour GROUP BY 1, 2, 3;

CREATE VIEW leak_monitor AS
SELECT d.machine_id, sum(d.hits)::float / sum(d.spins) AS hit_rate, g.hit_probability AS configured,
       (sum(d.hits) - g.hit_probability * sum(d.spins))
         / sqrt(g.hit_probability * (1 - g.hit_probability) * sum(d.spins)) AS hit_z
FROM meter_daily d JOIN machine_dim USING (machine_id) JOIN game_math g USING (config_id)
GROUP BY d.machine_id, g.hit_probability;

SELECT * FROM leak_monitor WHERE abs(hit_z) >= 5;   -- returns one row: M-1158

Chapter 3 · Downtime

3 · How much play was lost to downtime, and when?

Availability is 99.6%. What is lost sits in Ridgeline machines and understaffed shifts.

How we measured this

Lost theo = hours unavailable × the machine's theo per available hour in the selected period. Downtime is small (availability is about 99.6%) and concentrated: Ridgeline machines fault about 3.7× as often as Halcyon machines, and overnight faults wait about twice as long for a technician. The vacancies are new: in April and May the day shift ran at about 0.9 techs against 1.7 planned. With 0 techs a fault waits about 4.9 hours, with 1 about 1.2–2.6 hours, and with 2 about 0.1–0.7 hours. Refilling planned shifts is free and comes first. A paid extra technician ($11,520) would save only about $1k of theo a month, so it is not funded.

Chapter 5 · Comps

5 · What did the comp program cost, and did anything change?

On May 1 the comp point price halved, quietly adding $4.1M of potential liability.

How we measured this

Yes. On May 1, 2025, the point price of every comp fell from about 12.4 to about 5.8 points per $1 (−53%), overnight, for every item. Points earned per $ wagered did not change. After the change, comp cost per $ of theo rose, and coin-in did not.

Forecast model

Model: forecasting daily floor coin-in, validated without peeking

Gradient boosting cuts error 76% vs the baseline on an untouched May–Jun holdout.

How we measured this

Protocol. (1) Six candidates were compared with rolling-origin cross-validation inside Jan–Apr only: five 14-day folds, each trained on the days before it. (2) The model with the lowest CV error was selected. (3) It was frozen on May 1 and scored once on May–Jun. Event flags include only events announced before the forecast date, so the Locals Week (announced May 26) is excluded. Weather and tourism data published later are not used.

Leaderboard: 12 candidates, CV error (used to choose) vs holdout error

The ridge model with a trend term looked better in CV but failed on the holdout. This is why the test set isn't used to choose. Mean absolute error (MAE) is in dollars of coin-in per day.

How it changes decisions: (1) Staffing: July Saturdays are forecast at about 1.6× Tuesdays. The vacant day and swing tech shifts (Section 3) should be refilled first on Fri–Sun, where each hour of downtime costs the most. (2) Promotions: out of sample, Locals Week added only about +$11k theo over 7 days, inside the interval and below the $15k cost, so we don't fund a promotion weekend. (3) Measurement: the July forecast with its interval is the counterfactual for the sign and comp tests. A real effect has to push the actual line outside the band.

Code: analysis/model2.py (selection, conformal interval, July forecast) and analysis/model.py (first version). The interval is ±the 80th percentile of absolute CV residuals; it covered of holdout days against a nominal 80%, so treat it as slightly optimistic.
